## 1. Adapter versus direct admin: retain the boundary, reduce the machinery

**Retained:** CPA owns normalization, pricing, storage, retention, metadata projection and queries. Prox transports and displays those results. No second queue consumer, request database, browser pricing engine or generic CPA reverse proxy.

**Modified:** choose one authoritative CPA dataset and one explicitly configured homelab analytics grant attached to the already shared local auth scope. That grant permits reading the whole named dataset, including clearly labeled unattributed legacy history. Instance selection is a filter within that grant; it is not a new permission system. This is a proposed deployment contract, not a claim that the existing source declaration already grants CPA access.

The minimal adapter contract is:

- Reuse the existing server process and authentication primitive. Bind its authenticated shared scope to a fixed CPA destination, dataset identity, configured instance set and operational-detail field policy. Keep the CPA admin credential server-side. No browser-selected upstream URL or forwarded core key as CPA authentication.
- Allow only bounded retained-data queries and approved read-only rate/catalog operations. A full CPA credential inside the adapter remains broad authority; the adapter limits the operations it exposes. A new CPA scoped-token/RBAC system is unnecessary for this homelab release.
- Advertise analytics only for the configured local binding. An arbitrary external backend or different scope receives no local dataset access; it needs its own explicit binding or direct CPA login. Reuse source/session invalidation on logout, connection replacement and configuration changes.
- Before CPA supports instance filtering, expose only an explicitly labeled whole-dataset view to the whole-dataset grant. Never send an invented instance filter to the current decoder and assume enforcement. Mixed old rows stay unattributed; do not assign them to the active source.

The [source rules](/home/swerve/src/prox/src/domain/providerSources/RULES.md) establish explicit credential-sharing scopes and external-source separation. The [current server handler](/home/swerve/src/prox/server/app.ts:47) verifies a configured bearer key for quota operations; it does not already implement this analytics grant.

**Dissent preserved:** direct browser access with an explicit CPA admin login is the lowest-component option if a CPA-wide administrator view and that credential placement are acceptable. It still needs CPA semantic fixes, a separate client contract, origin/CORS handling and session isolation. CPA's `v0` spelling is not an objection: it is a different application's API. Keep Prox core calls on v8. Build only the selected transport initially; supporting both is optional scope.

**Acceptance consequence:** a dummy shared-scope caller can read its configured dataset, while an external session, forged instance/cursor and arbitrary destination cannot gain access. Switching source or logging out prevents stale publication. No real credentials are needed for these future tests. This replaces a speculative per-user/per-role authorization framework.

## 2. Identity and “every request”: withdraw execution-equals-attempt

The [core reporter](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/helps/usage_helpers.go:526) gives supplementary model usage a fresh UUID; [serialization](/home/swerve/src/CLIProxyAPI/internal/redisqueue/plugin.go:68) exports the record identifier as `execution_id` and the logging-context identifier as `request_id`. Therefore distinct execution IDs can describe supplementary image/model accounting, not retries. The reporter uses one-time publication for ordinary attempts, but that does not establish universal event cardinality.

**Modified definitions:**

| Unit | Meaning and counting rule |
| --- | --- |
| User request | One inbound inference operation at a declared proxy boundary, including rejection before provider admission. Group by verified instance-local inbound ID. A session or trace ID is a correlation field, not automatically this identity. |
| Execution / attempt | One actual upstream invocation. Retry/failover creates another attempt; supplementary accounting for work already represented does not. Count only producer-classified attempts, with explicit parent relationship and outcome. |
| Usage record | One accounting observation/component with its own stable record identity. Several records may belong to one attempt or request. Preserve the current wire `execution_id` losslessly without assuming its kind; use `unknown` until established. |

The future producer contract should identify inbound parent, actual attempt, record kind, and supplementary parent attempt. A separate `usage_record_id` can preserve the existing wire identifier while making its semantics explicit. Do not force every producer into `(instance, execution_id) = one attempt`. Component records must declare whether usage is additive or overlaps another record before parent costs are summed. Cumulative stream updates cannot be summed as separate charges.

Parent grouping initially means “observed usage linked to this request.” Count distinct proven parents in the selected usage cohort, publish linkage coverage, and explain when only some children match the time/model filter. A request-wide final result and end-to-end duration require lifecycle evidence; the last observed successful attempt cannot supply them.

**Safe migration:** CPA ingestion stamps the configured stable instance before deduplication. Add nullable producer/parent/kind fields and an identity version. Preserve existing row IDs, hashes and archive identity ledger. New records use a versioned instance-plus-record identity only where the producer guarantees its uniqueness; exact replay is idempotent and conflicting payloads are surfaced. Associate new identities with legacy rows only on deterministic evidence; ambiguous imports require reconciliation, not blind reinsertion or heuristic merging. Update ingestion, raw storage, projections, archive restore and queries together; retain original records and version corrected derived values. The [existing repository](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/repository/usageevent/repository.go:287) checks the identity ledger and inserts by `event_hash`, so changing only `buildEventHash` is insufficient. Previously collapsed events may be unrecoverable.

**Withdrawn:** every stream yields a usage row. `StreamUsageBuffer.Publish` [returns without publication when no usage was observed](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/helps/usage_helpers.go:982). The inspected [Claude stream](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/claude_executor_stream.go:351) and [Kimi stream](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/kimi_executor.go:373) contain deferred buffer publication without a universal `EnsurePublished` fallback. Pre-admission rejections are not usage events either.

**Acceptance consequence:** one inbound request with a failed attempt, successful retry and supplementary image record must retain all distinct accounting records, count two attempts only with proven kinds, and count one linked request. Replay/import must not duplicate cost. No-usage streams and rejected requests must appear in the future lifecycle ledger with unknown usage, not fabricated zero-token usage rows. Test equal legacy hash inputs across distinct instances/records and interrupted archive migration. These are proposed gates, not checks already passed.

## 3. Canonical tokens and known pricing defects: refactor, then fix

**Retained:** use the existing core canonical schema v2 and CPA owners. **Modified:** my “preserve existing arithmetic” instruction applies to the extraction/refactor step only. It cannot be the completed accounting behavior, and the other proposer's unchanged-arithmetic fixtures need the same correction.

The [core accounting contract](/home/swerve/src/CLIProxyAPI/sdk/cliproxy/usage/accounting.go:42) already supplies exclusive buckets and quality. CPA's [typed event and normalization](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/usage/event.go:17) preserve normalized cache input but lose canonical output partition, quality and usage-presence semantics. Arithmetic quality alone does not prove that usage was measured: an empty detail can normalize to valid zero buckets.

The [Gemini parser](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/helps/usage_helpers.go:1258) records candidate output and thoughts separately. OpenAI/Claude reasoning is included in output. CPA's [pricing input](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/service/pricing/cost.go:15) prices `OutputTokens` without a separate reasoning dimension. Thus positive Gemini thoughts can be omitted under a tariff that bills them as output. Adding reasoning globally would instead double-bill OpenAI/Claude.

CPA also [selects service tier without retaining effective outbound tier](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/usage/event.go:836), although core serializes it. Preserve requested, outbound and response tiers separately. Pricing selects the actually served tariff using protocol-specific evidence; do not blindly prefer the client request, or universally trust a response field when executor-specific behavior makes it ambiguous. Unknown applicability stays partial.

**Acceptance consequence:** first inventory duplicated arithmetic and callers with `rg`, consolidate under CPA usage/pricing, and compare representative before/after dumps with unchanged guards, rounding and clamps. In a separately verifiable change, preserve canonical output/quality/presence, fix provider-specific billable output and tier selection, and update all raw/rollup/row cost callers. With a synthetic applicable output tariff, Gemini candidates=50 and thoughts=20 bills 70 output tokens; inclusive OpenAI/Claude output=50 with reasoning=20 bills 50. Missing usage differs from explicit measured zero. Unsupported old projections report unavailable/partial coverage instead of retaining known wrong costs as complete. No pricing arithmetic belongs in Prox.

## 4. Rate completeness: modify the single-write-rate proposal

I accept the external researcher's primary-source findings: supported OpenAI models distinguish 30-minute/12-hour cache writes, and Anthropic distinguishes 5-minute/1-hour writes. These are model-specific rules, not universal multipliers or proof of local historical behavior. See the [external evidence and source register](phase2-external.md), especially O1/O2/O4 and A1/A3/A4/A6. I did not refetch those public pages in this phase.

**Withdrawn:** an aggregate cache-write count plus one matched model rate is sufficient for a complete estimate. CPA needs measured TTL buckets or defensible scoped evidence of the applicable lifetime. It must also resolve billing provider/model, effective tier/speed, context band, applicable modality/tool units and required regional distinctions. Only dimensions that affect the selected tariff need block completeness; a known zero write count does not require a TTL split.

Keep the first mode **estimated API-equivalent cost at current configured rates**. Return a book identity/as-of time and calculation version, known component subtotal, nullable complete amount, status and missing reasons. Status must account for missing measurements, ambiguous mapping, unknown TTL/tier and unsupported non-token units as well as missing rates. An explicit zero rate is evidence of a free component; a missing measurement is not. Missing monetary coverage cannot be quantified in dollars when its value is unknown: show record/component coverage instead.

Preserve input/read/write/output components, splitting writes by TTL where supported; include measured non-token charges under their own units. Token-only valuation is an explicitly partial subtotal if relevant tool/image/audio/runtime charges are unresolved. Model/provider aliases without authoritative mapping remain unresolved. A reference vendor rate can be shown as a declared reference basis, not a provider-specific contract price. Never invent prices for local aliases.

**Acceptance consequence:** include missing-usage-with-known-rate, ambiguous-provider, mixed-TTL, absent-TTL, explicit-free, tool-charge and tier/context boundary fixtures. At synthetic write rates 1 and 2 per million, 100 short-TTL plus 200 long-TTL tokens costs 0.0005; aggregate writes=300 without the split cannot establish that amount. Changing the current book may revalue old usage, but must change its displayed book identity. Historical effective-rate revisions are optional later work; observation date is never invented effective date.

## 6. Metadata: withdraw blanket diagnostic stripping

My Phase 2 default exclusions were too broad for the user's expressly requested metadata in a shared homelab admin dataset. Keep the ordinary table concise, but retain useful authorized operational fields in its detail view. This does not require a separate privileged-role system.

**Modified field policy:** the single configured dataset grant authorizes CPA's operational-detail projection. Include available bounded/sanitized IP, forwarding-chain and user-agent fields; request, session, parent-session and approved trace IDs; model/routing/tier/stream/effort fields; timestamps/outcomes; safe error summaries; owner-approved account/source labels; token/timing/cost provenance and approved response metadata. IP/forwarding values are observations, not proof of identity. Detail omission reasons distinguish absent, unretained, invalid and redacted values.

The [current monitoring projection](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/service/monitoring/service.go:4020) already includes IP/UA/session/header trace fields. Preserve their usefulness through CPA's owner policy; do not silently degrade the requested diagnostics. Its inclusion of token/key hashes is not permission to forward everything. Exclude credentials, secret fingerprints, authorization/cookie values, arbitrary headers, raw event JSON, raw error bodies and prompt/response bodies. Sanitize secret-bearing URLs and free text through the existing owner, before serialization. Bound and validate newly exposed correlation fields too.

**Acceptance consequence:** synthetic safe IP/UA/session/trace fields survive authorized detail reads while fake secrets in URLs, errors and headers never reach a response. Detail lookup and any future export enforce the same dataset authorization. Existing compatible JSONL deliberately omits some metadata; document that rather than silently widening its contract. Do not fetch raw bodies and rely on hiding columns in Prox.

## 7. Coverage and snapshot equality: retain a useful baseline, withdraw implied guarantees

CPA already supports useful retained-data charts and paginated details. Its [analytics service](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/service/monitoring/service.go:1009) can load an hourly snapshot while querying event pages separately. A price lock or [pricing/aggregate read transaction](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/store/store.go:650) does not prove every panel and later page uses one event population.

**Modified acceptance rule:** promise exact chart/detail reconciliation only when scope, filters, ingestion cutoff, raw/rollup checkpoint, accounting revision and rate book match, and details remain retained. Event-time bounds alone do not exclude late ingestion. A generated-at timestamp is not a snapshot watermark. The initial baseline may expose separate freshness/coverage and an explicit non-snapshot limitation; it must not advertise exact equality.

For the full interaction contract, CPA should return a query token binding these dimensions. Use a common supported cutoff or a complete raw fallback; otherwise identify the panel mismatch and refresh/disable exact drilldown. Bind cursors to that token. If retention removes detail during paging, expire the view or report the limitation rather than fabricating rows. Historical aggregates can legitimately exceed accessible detail counts. Unsupported rollup filters must fail or use complete eligible raw evidence.

**Retained:** latency and first-response metrics need compatible cohorts and sample counts. Existing output/full-latency is labeled full-execution output throughput. Do not derive generation speed from `latency - ttft` without compatible endpoints and numerator; preserve first-byte/first-content/unknown kinds. No p95 from sums/counts, and no average of instance p95s.

**Acceptance consequence:** inject late events, delayed rollups, concurrent price changes and raw deletion. Require equality only in a proven common snapshot, and visible limits otherwise. Pooled percentiles require eligible samples or a documented mergeable distribution. Collector freshness, retained-data availability, field presence and price completeness remain separate coverage dimensions.

**Delivery distinction:** a durable queue/outbox is unnecessary for this honest retained-events baseline. A stronger future “every inbound request since cutoff” target needs lifecycle capture before admission plus durable delivery, acknowledgement/replay and reconciliation through CPA persistence. A CPA post-commit outbox alone cannot repair loss before CPA receives the event. Durable downstream export is required only if a separate store/platform is chosen; neither is required now. Even future coverage must state its boundary and unresolved losses; history before that boundary remains limited.
