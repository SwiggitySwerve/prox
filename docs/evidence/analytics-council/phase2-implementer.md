# Phase 2 — Implementer: Prox request analytics

**Recommendation:** build a narrow, authenticated Prox adapter over CPA Manager's retained-data APIs. Extend CPA's existing usage, monitoring, and pricing owners to supply source-scoped results, explicit measurement coverage, and safe request details. Keep CPA Manager as the sole usage consumer. Prox should neither collect requests nor calculate their prices.

Research only, 2026-10-28. This proposal is one Phase 2 position for the Captain, not a council verdict or implementation authorization. Only this report was written. No subagents, other roles' reports, credentials, databases, queues, production endpoints, implementation, commits, or deployment were used. Findings describe the checked-out source, not deployed behavior. No visual scores were assigned.

## Decision and alternatives

| Option | Assessment |
| --- | --- |
| Browser uses CPA API directly | Fewest initial components, but introduces a second panel-auth session, couples Prox to a broad CPA response, and still requires CPA source attribution and measurement changes. Suitable for a standalone CPA viewer if separate login is acceptable; insufficient as an unchanged multi-instance Prox integration. |
| **Narrow Prox adapter over CPA** | **Recommended.** Reuse Prox's existing authenticated extension transport and server process. Adapter owns authorization, fixed upstream mapping, and transport; CPA owns accounting, query semantics, and safe projection. Adds no request store or consumer. |
| Dedicated service fed by the existing CPA collector | Consider only if CPA cannot meet measured query load or independent retention requirements. It would require an after-persistence, durable export/outbox with checkpoints, replay, and deduplication. An in-process callback alone is not that contract. More storage and failure modes than the current need warrants. |
| External observability platform | Useful later for tracing or operations, but does not repair missing CPA history or establish pricing semantics. Feed it through a CPA-owned export, never another destructive queue reader. Requires separate evaluation of retention, metadata exposure, and cost. |

The crux is whether the retained store can distinguish the configured proxy instances. The current normalized event does not carry that identity. A thin UI over today's endpoint can show combined retained events, but cannot honestly claim source-scoped completeness. Source attribution must precede the multi-instance release.

## Boundaries and contracts

### Ownership

1. **Core owns measurement.** Add absent provenance and event relationships at the existing usage reporter/record/payload boundary. CPA must not reverse-engineer true token arrival or inbound response completion from approximate numbers.
2. **CPA usage owns canonical events and accounting meaning.** Extend its rules document, normalizer, persistence models, and archive contracts. `Source`/`SourceHash` continue to describe credential identity; add `proxy_instance_id` rather than changing their meaning. CPA's usageidentity owner continues to own model/account identity rules.
3. **CPA monitoring owns queries, metric eligibility, coverage, and safe metadata projection.** Its service takes plain query/authorization-scope values, without HTTP request objects. Repositories implement persistence, while HTTP validates and serializes service results.
4. **CPA pricing/modelprice own monetary rules and price selection.** Extend existing owners with typed availability and provenance results. Prox receives amounts and components; no JS copy of cache arithmetic, tier rules, price matching, or provider classifications.
5. **Prox providerSources owns configuration, aliases, discovery, and source lifetime.** Extend that owner for private CPA bindings and public capability metadata.
6. **Prox analytics adapter owns transport and access enforcement.** It does not inspect CPA SQLite, raw JSON, price tables, or internal caches. A small new server package is justified because quota does not own request analytics transport. The browser feature owns interaction, formatting, and chart geometry only.

### Adapter authorization and discovery

Use the existing server process and source-bound extension path. Proposed browser operations are `/v8/management/prox/analytics/{capabilities,summary,requests,prices}` under a configured source route. Route generation must preserve a server-validated route/source binding when forwarding to the adapter. Do not trust a browser-provided instance header or arbitrary upstream URL.

The adapter authenticates the caller against the configured scope and derives the allowed instance set from the providerSources owner. A key valid for instance A does not permit B solely because both are in discovery. The existing single history key is only reusable if the operator explicitly declares all those sources share the same analytics access scope. Otherwise extract the existing verification primitive once and support per-scope verification. Alias routes resolve to the same identity and permissions.

The adapter uses a separate server-side CPA panel credential reference. Never forward the browser's core key to CPA or expose the panel credential to the browser. For the first release, restrict upstream operations to read queries and catalog reads; no model-price sync/update, setup mutation, catch-up request, archive restoration, or queue operation is reachable. CPA remains responsible for projecting fields allowed for that read purpose. A full panel credential remains broad authority inside the trusted adapter; a dedicated scoped CPA read credential would reduce that authority but is a separate auth change, not an existing feature to assume.

Public discovery advertises only supported contract version, fixed relative adapter route, analytics auth-scope identity, and capability availability. Private bindings hold CPA origin, credential-file reference, and canonical instance mapping. Reject browser-selected URLs, redirects to another origin, unknown sources, malformed capability documents, and response-schema mismatches. Preserve no-store responses and bounded request/response sizes. Use sanitized errors that distinguish unauthenticated caller, forbidden scope, CPA unavailable, unsupported capability, and incomplete coverage.

The deployment may use one CPA store for several instances. Query it once per scope, with a validated instance filter; do not query the same combined store once per instance and add duplicate totals. Initially support one authoritative CPA store per deployment scope. If the actual deployment has several stores, map each instance to exactly one store and design federation separately: additive totals are possible, but percentiles and cursor pages cannot be combined by averaging or concatenating arbitrary responses.

Capture Prox sessions and feature leases for every request. Cache identity includes auth scope, source generation/epoch, source-set revision, filter, and price-book revision. Clear on logout/reconfiguration. An absent adapter on a portable external backend means analytics unavailable; it never authorizes a v0 core fallback or queue probe.

### Canonical event and request schema

The following is a proposed additive contract, not fields asserted to exist today:

| Group | Required semantics |
| --- | --- |
| Identity | `schema_version`, stable `proxy_instance_id`, collector binding revision, opaque persisted event ID, identity version, nullable inbound `request_id`, nullable `execution_id`, nullable `parent_execution_id`, `trace_id`, `event_kind` (`attempt`, `additional_model_usage`, `unknown`). Store collector identity separately from user metadata. |
| Time | Event timestamp, ingestion timestamp, nullable start/end measurements and measurement origin. Label existing reporter duration `execution_latency_ms`; expose `request_response_ms` only with an inbound completion measurement. |
| Model/routing | Provider, executor, requested/resolved/response/analytics/billing model, endpoint/method, streaming flag, requested/effective service tier, reasoning effort. Keep session ID and parent-session ID separate from request and execution identity. |
| Tokens | Raw reported values plus canonical uncached input, cache read, cache creation, total input, output, reasoning, total; units and accounting version. Include per-field presence/quality (`reported`, `derived`, `unknown`). Never add reasoning to output without the provider owner's contract. |
| Result | Execution result, safe error category/status/summary, nullable request terminal result, attempt-grouping quality. Failed attempts can still carry chargeable tokens. |
| Timing quality | TTFT value and kind (`substantive_token`, `first_byte`, `first_packet_fallback`, `legacy_unknown`, `missing`), clock origin, eligible generation duration, and why a metric is unavailable. |
| Price | Nullable equivalent USD cost and components, resolved pricing identity, rate source, price-book revision, valuation basis, availability and missing-price reason. Amount zero is distinct from unknown. |
| Metadata | Opaque credential/client-key references, safe labels, allowlisted response metadata, and explicit field availability. Default output excludes raw payloads, fail bodies, credentials, arbitrary headers, full forwarding chains, and access-token hashes. Restricted metadata, if needed, requires authorization in the owner before serialization. |

Bind `proxy_instance_id` from trusted collector configuration **before** normalization finalizes persisted identity. Validate it against an explicit mapping generated from the deployment's source owner. Duplicate alias URLs must not create two collectors. Adding a source to Prox does not automatically start collection; the existing CPA collector configuration must explicitly own that source. Extra collectors currently reuse a primary key; distinct key scopes require extending CPA's collector binding rather than assuming that reuse is valid.

New identity must include instance and execution semantics. Preserve old event hashes and ledger entries. A versioned v2 hash can identify new events while legacy hashes remain available for proven import/replay matches. When no execution ID exists, retain the legacy fingerprint with instance qualification and mark its limitations. If identity repeats with a different payload, surface a conflict rather than silently overwrite. Do not claim older hash collisions or dropped records can be recovered.

Requests are a **projection over events**, not a renamed event table. Group only validated full inbound IDs within an instance. Expose observed execution count and supplementary-model events separately. Rows with missing or ambiguous parent identity remain ungrouped. Request success and response duration require terminal inbound evidence; choosing the last event, maximum latency, or sum of retry latencies is not sufficient. The first release may display “observed executions” with a request drilldown and unavailable terminal metrics, but must not label those counts as complete client requests.

### Read API contract

Keep CPA's existing endpoint compatible. Add a versioned read DTO/service entry under its monitoring owner, and have the Prox adapter map that contract into the extension routes. The initial implementation can reuse the existing query machinery rather than create separate storage or aggregation logic.

| Proposed operation | Contract |
| --- | --- |
| `GET …/capabilities` | Contract version; supported source IDs; collector freshness; known collection start; raw-detail retention bounds; available aggregate fidelity; identity/timing schema support. Separate configured, authenticated, collecting, stale, unavailable, and unsupported states. |
| `POST …/summary` | Validated half-open `[from_ms,to_ms)`, explicit timezone/bucket size, authorized instance IDs, provider/model/status filters, and requested aggregate sections. Return totals, time buckets, provider/model breakdowns, timing distributions, price coverage, and a query snapshot token. No raw events are required for summary rendering. |
| `POST …/requests` | Same immutable query scope plus opaque cursor, bounded limit (propose default 100, maximum 500), and explicit row mode (`executions` or supported request grouping). Return allowlisted rows, next cursor, has-more, and detail coverage. Counts must describe their row mode. |
| `GET …/requests/{opaque-id}` | One authorized request/execution detail and its known relationships. Missing, forbidden, expired cursor, and raw detail removed by retention must be distinct contract outcomes without leaking another scope's identifiers. No raw database-row passthrough. |
| `POST …/prices` | Source-scoped registered-model inventory joined by CPA's price resolver. Return provider grouping, registration evidence/time, alias/billing identity, rates per million input/output/cache-read/cache-write tokens, explicit units/currency, context/service-tier bands, source/revision, and missing/ambiguous matches. Includes models with no retained traffic. |

The cursor must bind filter hash, authorization scope, source-set revision, row mode, timestamp/ID keyset, and a maximum ingested row ID or equivalent watermark. Validate or authenticate it server-side and reject changed scope/filter. Use CPA's existing timestamp+ID ordering, including same-timestamp fixtures. A frozen event watermark prevents late backfilled events from appearing halfway through the scan. Include price-book revision; if rates or retention/attribution change mid-query, either serve a retained snapshot or explicitly invalidate it. Do not promise a consistent view merely because an opaque cursor exists.

Summary and detail share the same scope and snapshot semantics. A rollup may participate only if its checkpoint can establish the same event watermark; otherwise use eligible raw rows or explicitly report that snapshot fidelity is unavailable. Exact totals and percentiles come from the owner over eligible observations; no averaging instance percentiles, no summing overlapping raw and rollup ranges, and no total built from only the visible page. Restrict query span, bucket count, filter cardinality, and execution time based on measured query plans. Existing CPA's 50,000-event page allowance is not a suitable default for this UI.

Coverage travels with every section: requested/available range, included sources, missing or stale sources, raw versus rollup fidelity, known deletion ranges, unknown-attribution count, eligible/total measurement count, priced/unpriced count and token totals, and explicit collection-gap knowledge. CPA's current `RawComplete` describes retained/deleted data; it does **not** prove every upstream request was captured. “No known deletion” and “complete traffic capture” are different claims.

### Price and speed presentation semantics

Use current-rate equivalent API cost for the smallest release. It answers the user's cost question using the existing pricing engine without inventing historical invoices. Return known subtotal and unpriced coverage separately; a partial total must not look complete. Preserve configured free rates, fallback cache rules, context bands, and service tiers. If immutable historical valuation is later required, add a versioned price book or event-time rate snapshot under CPA pricing; do not retroactively label today's rates as event-time rates.

The registered-model table groups by instance/provider and left-joins pricing, preserving unpriced models. `owned_by` alone is not proof of the routed provider; obtain provider membership from authoritative registry/credential configuration or return unknown/multiple. Expose the current model-only price scope honestly. Do not create provider-specific numeric rates unless the pricing owner gains explicit provider/model keys and migration rules. Existing CPA runtime discovery must be made multi-instance and v8-compatible; do not copy its legacy-core calls into Prox. Pure catalog discovery must not invoke price synchronization or a provider inference request.

Display execution latency and recorded TTFT with provenance. The existing `output_tokens / full_latency_seconds` is an effective throughput metric. True generation rate needs output tokens and a measured generation interval with compatible boundaries; subtracting existing TTFT from total latency is unsafe because their start points differ. Do not compute a rate for missing/zero/negative intervals, missing output usage, or unsupported stream semantics. Keep reasoning tokens separate, and return eligible sample counts for p50/p95 and any throughput distribution. Failure and non-streaming samples need explicit inclusion policies.

Charts consume server-provided values and coverage: token categories over time, cost by provider/model, throughput and latency/TTFT distributions, and request/execution outcomes. Missing intervals break lines or show an unavailable band. A zero bucket is permitted only when the owner establishes zero observed activity for the applicable coverage definition. The request table exposes every **retained authorized row**, with a metadata inspector and reasons for missing fields; it cannot promise every request ever sent.

## Smallest robust implementation sequence

These are proposed future changes, in dependency order. The Captain's UI release remains separate; no release files or other edits were changed for this research.

1. **Freeze definitions and produce synthetic baselines.** Agree on event versus request labels, current-rate valuation, metric origins, source authorization, and safe metadata. Record representative normalized token/cost/aggregate outputs before changing owners. Search for all existing copies before extraction. Keep any behavior-preserving refactor independently verifiable from behavior changes. This is especially important for cache normalization and pricing.
2. **Extend CPA identity and source bindings.** Add nullable fields, ingestion-time source attribution, identity versioning, and source-aware queries. Update primary and extra collectors in place; never start a parallel collector. Carry fields through raw persistence, identity ledger, rollups, archives/import, and public DTOs. Source filters unsupported by an older rollup must fall back only to complete eligible retained rows or report unsupported coverage, never use the unscoped rollup.
3. **Add measurement provenance at core, then preserve it through CPA.** Reuse parent/execution IDs already emitted. Add event kind/parent-execution link and timing-origin information; add inbound terminal measurements only where a real request-lifecycle owner can measure them. Keep old producers supported as `legacy_unknown`. Token presence is also needed: `EnsurePublished` can emit an empty usage detail, so numeric zero alone is not proof of measured zero usage. This producer work is required for strong speed/response-time claims, not for a clearly labeled legacy-data preview.
4. **Extend CPA read contracts and pricing coverage.** Reuse monitoring queries and keyset pagination. Add snapshot scope, source filtering, eligible sample counts, owner-side safe projection, per-row cost, and explicit price status. Reuse arithmetic unchanged first; verify baseline outputs. Extend model-price discovery across configured instances via v8 and preserve provider membership. Do not add a second price engine in the adapter.
5. **Add the narrow Prox adapter.** Reuse the server process, fixed route generation, source manifest, and authentication primitive. Add explicit CPA binding and per-scope authorization; share existing primitives rather than duplicate them. Fail closed on unknown source/schema, and preserve partial availability as a visible result. Ensure retries of read requests cannot trigger collection or writes.
6. **Build the analytics feature after the Captain's UI release.** Use feature-owned page/hooks/components, the shared UI primitives, translations, and source leases. Render server results with request detail pagination. Keep core v8 and single-file/hash-router deployment contracts. Start behind an explicit analytics capability; absence of capability leaves existing features intact.
7. **Validate on disposable fixtures, then stage rollout.** First enable CPA readers and compatible schema; then update its existing collectors and core emitters as needed; then enable the adapter for a known source scope; finally expose the tab. Compare fixed-range summary, detail, and price totals with a known synthetic CPA ledger before expanding scope. Rollout operations require a separately authorized implementation session.

## Retention, backfill, and reversibility

**History:** CPA's retained raw rows and verified archives are the only potential detail backfill sources. The destructive queue is not a recovery mechanism. Existing rollups can supply only their supported dimensions and fidelity; they cannot regenerate request rows, missing identities, token timing, or metadata. Restore through CPA's archive/import owner in a separately authorized maintenance action, not a page-load side effect.

**Attribution:** old multi-upstream rows remain `unattributed` unless there is independent, deterministic evidence binding that row/range to one configured logical instance. Provider, model, credential filename, account email, and event Source are insufficient on their own. Store any approved legacy attribution as an additive mapping with evidence/revision, not a rewrite of the raw event. Removed instances remain historical identities and are not reassigned to a new backend. Unattributed history is visible only to a scope authorized for that whole legacy dataset; it cannot be included in a narrower source subtotal.

**Migration:** use additive nullable columns and versioned derived projections, indexed by instance/time/row ID for supported queries. Preserve existing event hashes and primary keys. Keep a versioned identity association for new execution-aware identities and proven legacy replay matches; exercise both raw and archived identity-ledger deduplication. Do not simply change `buildEventHash` and reimport the whole store. The existing unique event-hash constraint makes careless identity rewrites particularly dangerous.

Backfill in bounded, resumable batches under the existing maintenance owner, with checkpoints and output-count checks. Rebuild only projections supported by retained evidence; publish completeness per source/range. Preserve previous projections until new ones reconcile. If deleted raw data makes a new dimension unrecoverable, mark that range unsupported instead of filling it from current inventory. Keep archive verification/deletion gates intact and update archive schema compatibility tests before new fields enter retention.

**Rollback:** disable discovery capability/UI and adapter routes first; CPA keeps collecting. Disable new readers without dropping fields or derived tables. Source attribution mappings can be retired by revision, and new projections can be discarded/rebuilt without changing immutable raw rows. Collector/schema binary downgrade is a separate compatibility test: do not assume an old writer understands v2 identity or archive records. If that test fails, retain the compatible collector and roll back only consumers; an unsupported writer downgrade requires an offline verified backup/restore plan. “Additive” alone does not prove lossless rollback.

No initial rollout should change retention duration, purge history, automatically restore archives, or start an additional consumer. Queue delivery can still lose events during downtime, expiry, process restart, or a destructive-read/persistence failure; this proposal makes coverage honest rather than claiming exactly-once collection.

Release gates: unchanged baseline numerical outputs after any refactor; fixture contracts passing in all three affected owners; representative SQLite query plans and load measured on disposable data; build/type/lint checks required by each affected repository; browser verification for pagination, source changes, omitted-data charts, metadata access, keyboard operation, and narrow layouts. The Captain can apply visual scoring later; it is outside this research.

Concrete accounting oracle: with explicit synthetic rates of $2 input, $8 output, $0.20 cache read, and $2.50 cache creation per million tokens, 850 uncached input + 100 cache read + 50 cache creation + 200 output costs **$0.003445** before display rounding, with no tier premium. An inclusive input report of 1,000, a separate input report of 850, and a read-inclusive/write-separate input report of 950 must produce that same canonical result when their explicit accounting modes apply. Concrete timing oracle: 100 output tokens over a measured 2-second execution gives 50 tokens/second effective throughput; a separately measured compatible 1.5-second generation interval gives about 66.667 tokens/second generation rate. Without that interval/provenance, generation rate remains unavailable.

## Missing runtime facts that change implementation scope

- Deployed core/CPA versions and whether they match these checkouts; producer ID/timing/token-presence formats in sanitized samples.
- Number of authoritative CPA stores; exact source-to-collector bindings; which configured Prox sources are actually collected; duplicate collectors/aliases; auth-scope compatibility. No credential values are needed for the design.
- Effective queue transport/TTL, collection freshness, observed gaps/dead letters, and known restart history. Source inspection cannot establish complete traffic coverage.
- Raw retention settings and bounds; archive availability/verification; rollup completeness and supported dimensions; volume and representative query latency. Existing defaults do not establish deployed retention.
- Whether any trusted historical provenance can resolve old instance identity. With multiple collectors and no retained origin, complete attribution may be permanently impossible.
- Actual provider membership available from runtime catalogs, especially aliases and OpenAI-compatible routes; whether CPA's deployed core client is already v8-adapted beyond this checkout.
- Price-book freshness, sources, explicit free values, conflict policy, and whether the desired valuation is current-rate equivalent cost or immutable historical valuation. This proposal deliberately chooses current rates for the first release.
- Which metadata the intended Prox operator may view. “Every request metadata” requires a field inventory and server authorization contract, not a raw-object export.
- Whether exact inbound response time and post-first-token speed are required at launch, or a first release with truthful execution latency/recorded-TTFT labels is acceptable. Their absence must remain visible either way.

The minimum honest delivery is a source-scoped dashboard over CPA's retained evidence, with current-rate costs, known execution details, and visible omissions. Complete historical traffic, exact client-request outcomes, and true generation timing remain conditional on evidence the present normalized ledger does not supply.
