## 1. Integration and the smallest authorization contract

**Retained:** CPA is the sole usage consumer and owns normalization, storage, pricing, retention, queries, and metadata projection. Prox owns presentation and bounded transport. No additional database or observability platform is justified by the evidence.

**Modified:** use one fixed CPA destination and one explicitly configured shared analytics dataset for the current homelab. Reuse the existing same-origin server process and bearer-verification primitive, with a server-side binding from the shared Prox auth scope to that dataset. All callers authorized for this declared scope may inspect its full retained history, including unattributed historical rows. Instance filters select data within that authorization; they do not grant authority. Query the shared store once, not once per route alias.

The private binding contains the CPA origin, a separate CPA-admin credential reference, dataset identity, and the exact participating Prox instances/auth scope. The browser supplies neither upstream URLs nor CPA credentials. Initially allow only bounded analytics queries and approved catalog/price reads; no generic pass-through, queue subscription, sync, setup, import, archive mutation, or price editing. One shared scope needs no roles, permission database, delegation protocol, or per-user framework. An external backend or different scope receives no local analytics capability merely because a connection exists; an unsupported binding fails closed. Preserve source/session invalidation and LAN/single-file UI behavior.

This is a proposed binding, not an existing permission feature. [Prox source rules](/home/swerve/src/prox/src/domain/providerSources/RULES.md) expressly distinguish configured scope sharing from verified live authentication. [The server handler](/home/swerve/src/prox/server/app.ts:47) currently verifies one key file for quota operations; it does not already map CPA datasets.

**Withdrawn:** my Phase 2 description of direct reuse as generally insufficient was too strong. A distinct CPA-admin session intentionally authorizing the whole CPA dataset is legitimate for this personal admin product. CPA's `/v0/management/monitoring/analytics` spelling is no reason to reject it: this is CPA's application API, while Prox's core traffic stays on v8. Direct access avoids adapter code but puts CPA-admin authority in the browser and requires a separate endpoint/session and origin arrangement. I still choose the adapter for same-origin credential placement and its smaller browser-accessible surface. If those benefits are not wanted, direct admin is the lower-component-count dissent; both options require the same CPA semantic fixes.

**Acceptance consequence:** synthetic shared-scope callers can read the declared dataset; an unrelated external connection, unknown scope, forged instance, retargeted cursor/detail request, or arbitrary upstream URL cannot. CPA credentials never enter browser responses or errors. Unsupported instance filtering must be rejected rather than silently ignored. Until attribution exists, the initial view is explicitly dataset-wide and has no pretend per-instance selector.

## 2. Requests, attempts, usage records, and migration

**Retained and sharpened:** one inbound request can trigger multiple attempts and supplementary usage records. A new core execution ID does not prove a retry. [The reporter](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/helps/usage_helpers.go:526) gives an additional-model record a fresh UUID. [The payload](/home/swerve/src/CLIProxyAPI/internal/redisqueue/plugin.go:68) keeps inbound request ID, execution ID, trace ID, and session hierarchy separate.

Use these explicit future definitions:

| Unit | Meaning and counting rule |
| --- | --- |
| User request | One inbound inference operation received at the proxy ingress boundary, including an operation subsequently rejected before execution. A WebSocket submission is an operation; the entire socket/session is not one request. Count from lifecycle identity and terminal state, not from usage rows. |
| Execution/attempt | One actual upstream invocation. Record its relationship to the inbound request and whether it is initial, retry/failover, or an internal child invocation. Preserve existing execution IDs without assuming their historical cardinality. |
| Usage record | One immutable accounting observation, with its own idempotency identity and kind. A supplementary image/model record can belong to an existing attempt; it contributes usage/cost without adding a retry. If it represents a real separate invocation, record that relationship explicitly. |

Core should emit record kind and parent execution/attempt links where it knows them. Preserve request ID, trace ID, and session/parent-session independently; none is an automatic substitute for another. CPA groups by `(instance, inbound request identity)` only when producer semantics establish that identity. Count retries from explicit attempt relationships, not `distinct execution IDs > 1`. Parent counts across model/time filters are not additive, and a group selected through one matching record must say whether its other records fall outside the filter. A parent outcome requires authoritative lifecycle termination, not the last successful usage row.

**Modified migration:** retain legacy event hashes, row IDs, and identity-ledger entries. Introduce versioned identities for new records, minimally `(instance, producer usage-record ID)` under a documented immutable-record contract; an existing execution UUID can supply that record ID only where one-record semantics are proven. Carry separate attempt/group relationships. Bridge old/new identities only on deterministic evidence. Replaying a known old archive must hit its original identity; ambiguous legacy matches must be reported and held for reconciliation rather than silently merged or inserted again. Same identity with changed content is a conflict, not an overwrite. Never wholesale rehash history. Additive fields, compatible readers, archive preservation, and resumable projection rebuilds precede switching writers; old-writer rollback requires compatibility evidence. [CPA's current identity ledger](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/repository/usageevent/repository.go:380) makes this more than a UI grouping change.

**Withdrawn:** universal publication cannot be inferred from `EnsurePublished`. [StreamUsageBuffer.Publish](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/helps/usage_helpers.go:982) returns without publishing when usage was not observed. Successful [Claude](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/claude_executor_stream.go:350) and [Kimi](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/kimi_executor.go:372) stream paths use it without a universal empty-row fallback. Pre-admission failures are not usage events at all. Existing counts remain “retained usage records”; grouping improves interpretation but does not establish ingress coverage.

**Acceptance consequence:** one failed attempt, one successful retry, and one supplementary record produce one evidenced inbound group, two attempts, three usage records, and each billable component once. Exact replay and archive restore add nothing; differing instances remain distinct. A successful no-usage stream and an admission rejection appear in the future lifecycle ledger with appropriate usage availability and no fabricated usage row. Legacy unknown relationships remain unknown.

## 3. Canonical accounting and known pricing defects

**Retained:** normalize and calculate in the CPA owners; no formulas in Prox rendering or the adapter.

**Modified:** consume the existing [core schema-v2 accounting](/home/swerve/src/CLIProxyAPI/sdk/cliproxy/usage/accounting.go:41), including exclusive output buckets and quality. CPA currently uses canonical evidence for cache normalization but does not preserve the full output/quality/presence contract in its [typed event](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/usage/event.go:17). Preserve canonical measurements through ingestion, persistence, archives, projections, queries, and DTOs. Add explicit measurement presence at the producer: an arithmetically complete all-zero breakdown does not prove provider-reported zero usage. Do not invent a competing canonical schema in Prox.

**Withdrawn:** “reuse arithmetic unchanged” is only a refactoring step, not the final correctness condition. [Gemini parsing](/home/swerve/src/CLIProxyAPI/internal/runtime/executor/helps/usage_helpers.go:1258) places candidates in legacy output and thoughts separately; OpenAI/Claude output includes reasoning. [CPA pricing's ModelTokens](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/service/pricing/cost.go:15) prices output without a separate reasoning field, while existing aggregate reads sum legacy output. Gemini thoughts can therefore be omitted from an output-priced estimate. Fix billable output using validated canonical semantics; never add reasoning globally.

Likewise, core emits requested, effective outbound, and response service tiers. CPA's [tier resolver and normalization](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/usage/event.go:224) omit effective outbound tier and have a Codex request-tier preference. Preserve all three inputs, then define provider-specific billing resolution: use authoritative served-tier evidence where valid, effective outbound settings where that is the documented billing basis/fallback, and expose unresolved conflicts. Do not blindly replace one universal precedence rule with another. Requested `auto` is not proof of standard billing.

Sequence the work as behavior-preserving consolidation with representative before/after token, cost, and aggregate dumps, followed by separately verifiable correctness changes. Search for all arithmetic copies and move consumers to CPA's authoritative result; the existing CPA browser arithmetic must not become a third Prox implementation. Record normalization and calculation versions. Rebuild affected projections only where retained evidence supports the corrected result; unsupported historical ranges remain partial. Known-wrong components must be withheld or explicitly excluded from a partial subtotal until corrected.

**Acceptance consequence:** the same synthetic input=100, output=50, reasoning=20 means 150 total tokens for inclusive OpenAI output, but 170 for Gemini's separate thoughts, with Gemini billable output=70 when the applicable rate charges thoughts as output. Claude's separate cache inputs are additionally included under its own contract. Test canonical-quality/presence propagation, cache mirrors, output-only/reasoning-only usage, changed outbound tiers, and raw/rollup parity. A passing behavior-preservation test alone does not pass the corrected-cost gate.

## 4. Pricing coverage includes measurements and applicability

**Retained:** initial valuation is “Estimated API-equivalent cost at current configured rates,” with book revision/as-of time and calculation version. Historical effective-rate valuation is optional. Neither current prices nor a frozen snapshot proves applicability to an old request.

**Modified:** the [external report](/home/swerve/src/prox/docs/evidence/analytics-council/phase2-external.md) verifies model-specific OpenAI 30m/12h write rates and Anthropic 5m/1h writes, effective-tier distinctions, and token/non-token units. Accept those schema requirements; do not turn them into provider-wide default tariffs. An aggregate write count cannot select different TTL rates. Preserve TTL splits as subdivisions, never add the aggregate write field again. Missing TTL is harmless only when writes are known zero or a verified applicable rule makes TTL immaterial; otherwise the relevant component is unknown. A declared configuration-based assumption must remain an estimate with its provenance, not a measured historical split.

CPA's cost result should carry nullable amount/known subtotal, currency/unit, selected billing model/provider mapping, tier/context/TTL rules, price provenance, valuation revision, measured components, status, and reasons. `priced`, `partial`, `unpriced`, and `explicit-zero` must depend on both rate applicability and measurement availability. Reasons include absent usage, unknown TTL, ambiguous provider/model, unresolved tier, invalid canonical partition, missing tariff, and unsupported tool/media units. A matched price row is insufficient. Zero-token media/tool work is not automatically free; failed attempts can have charges. Do not manufacture bounds when missing dimensions could add unknown costs.

The model table enumerates all authorized registered models, including unused/unpriced entries, and shows provider/route identity, local alias, authoritative upstream mapping if known, reference rates and expanded TTL/context/tier schedules. The present model-keyed book may serve as an explicitly shared reference price, not an assertion of provider-specific contracts. No inferred Astra/Terra/local-alias rates, guessed upstream publisher, or invented effective dates. Current registrations and historical usage remain different populations.

**Acceptance consequence:** two records with equal aggregate cache writes but different measured TTL splits can cost differently. Missing TTL cannot become a complete estimate merely because the model exists in the price map. Exercise missing usage, explicit zero rates, provider ambiguity, model-specific thresholds, served-tier conflicts, and non-token units. Show complete-event count and partial/unpriced reasons separately from component subtotals; unknowns cannot silently enter average-cost denominators as zero. External report fixtures remain proposals, not tests executed here.

## 6. Preserve useful authorized metadata

**Modified:** withdraw blanket removal of useful diagnostics. The user expressly requested every request's metadata. For the declared shared homelab dataset, details should retain all available owner-approved operational fields: request/execution/record and trace IDs; session/parent-session IDs; client IP, forwarding chain, and user agent; sanitized method/path/endpoint; provider and model identities; streaming/reasoning/tier settings; safe credential/account labels; status and bounded failure summary; permitted response diagnostics; measurement and price provenance. Unknown, truncated, redacted, and unavailable are distinct states.

The [current monitoring projection](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/service/monitoring/service.go:4020) already returns IP/forwarding/UA/session and diagnostic fields; retain that operational value. Extend CPA's owning projection for missing safe fields. [Persistence sanitation](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/usage/persistence_security.go:649) remains necessary but is not itself a field-authorization policy. Dataset authorization and the fixed detail-field policy run server-side before serialization. Default summary rows can be smaller without deleting detail metadata.

Never expose credential values, authorization headers, raw event JSON, prompt/response bodies, or raw failure bodies. Do not bulk-copy arbitrary headers/query strings. Existing token fingerprints are not needed for this brief: use owner-approved opaque credential identifiers/labels instead. Preserve owner-specific exclusions on exports; a detail expansion is not permission to widen a separate export API. No new role hierarchy is required.

**Acceptance consequence:** synthetic IP/UA/session/trace diagnostics survive an authorized detail read, while secret sentinels embedded in URLs, errors, headers, and nested data never do. Unauthorized dataset/detail/cursor access returns no metadata. Missing trace or session fields stay unavailable; they cannot be reconstructed from unrelated IDs. The field inventory and unavailable reasons must cover the full requested detail surface, rather than calling a stripped summary “all metadata.”

## 7. Useful baseline, honest snapshots, and future delivery

**Retained:** a baseline adapter over existing CPA retained reads is useful now in principle. It needs no new durable queue or outbox to honestly display retained events. Keep archive/raw-availability limits separate from ingestion continuity, measurement presence, and price coverage.

**Modified:** a timestamp/ID cursor is not automatically a report-wide snapshot. [CPA monitoring](/home/swerve/src/CPA-Manager-Plus/apps/manager-server/internal/service/monitoring/service.go:214) exposes retention coverage and pagination; it does not by that fact promise identical populations across independently advancing rollups and detail reads. Baseline sections report their as-of/coverage limitations and do not promise exact chart/detail equality. The stronger read contract needs matching dataset/source/filter scope, immutable ingestion bound, rollup coverage checkpoint, normalization/calculation version, and price revision. Pin or detect changes across pages; late insertion, retention, and price changes cannot silently shift a frozen report. If a rollup cannot answer at the same bound, use eligible raw data or disclose/withhold reconciliation. Aggregate-only history can legitimately exceed available details.

No invented percentile: use eligible raw observations or a declared mergeable distribution with its error semantics. Sums/counts and averaged instance p95s cannot supply a fleet p95. Preserve unavailable values and sample counts. Initial timing labels remain recorded execution duration, recorded first-response delay with unknown/mixed method, and output/full-duration throughput. True proxy-observed first-content timing and generation-window estimates require aligned clocks, provenance, output presence, and explicit stream/outcome eligibility; no subtraction of incompatible clocks and no claim of browser-perceived latency.

**Future stronger coverage:** record inbound start/termination before admission and through downstream completion/cancellation; independently preserve execution and usage observations. Select a declared future cutoff, covered instances/transports, and supported inference routes. Add durable producer-side capture with acknowledgement/replay into the existing CPA consumer, stable idempotency and recovery checkpoints. A CPA outbox after insertion alone cannot recover losses before CPA persistence. A downstream export outbox is needed only if a new sink is chosen; it is not required for this dashboard architecture. Explicitly track incomplete lifecycles, gaps, and bounded retention. Requests that never reach the declared proxy ingress are outside this observable denominator.

**Acceptance consequence:** force rollup lag, late rows, price edits, and expired detail during synthetic pagination. Either matching-watermark results reconcile or the API reports why they cannot. For the future coverage claim, exercise admission rejection, no-usage success, retry, cancellation, producer/consumer crash, restart, duplicate replay, and backlog recovery. Every durably observed inbound operation remains accounted for, including incomplete termination; unsupported intervals stay gaps. Do not claim uninterrupted capture through untested ingress/storage failures.
