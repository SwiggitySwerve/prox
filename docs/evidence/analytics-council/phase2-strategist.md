# Phase 2 — Strategist: Prox request analytics

**Recommendation:** expose CPA Manager's retained analytics through a narrow, authenticated Prox adapter. Keep CPA Manager the sole usage consumer and owner of normalization, pricing, persistence, and analytical queries. Extend its contracts where identity, measurement provenance, and price coverage are missing. Prox owns source selection and presentation, not a second accounting engine.

**Decision crux:** can CPA supply an authorized, instance-attributed, redacted query contract over its retained data? The inspected code supplies much of the query machinery, but does not yet establish that complete contract. Building charts first would conceal these gaps.

Research date: 2026-10-28. This is one Phase-2 proposal for Captain synthesis, not a council verdict or implementation authorization. Only local source was inspected. No production calls, credentials, queue reads, database reads, implementation, commits, deployment, subagents, or other roles' report reads were performed. No UI scores are assigned. Findings describe the inspected checkout, not deployed capability or historical traffic completeness.

## 2. Architecture comparison

Effort is relative to existing repositories. Estimates assume one experienced engineer, synthetic fixtures and access to maintain both projects later. They are planning ranges, not measured delivery commitments; data-contract repairs are shared costs across options.

| Option | Strength | Main cost or failure mode | Assessment |
|---|---|---|---|
| A. Prox browser queries CPA directly | Fewest runtime components; retains CPA ownership and can fit portable single-file hosting. | A separate CPA panel login/auth scope, CORS, service discovery and session isolation are required. Broad existing responses may expose more metadata than the dashboard needs. Multi-instance identity gaps remain. A core management key must not be assumed to authorize CPA. | Useful for an explicitly configured single-CPA deployment after CPA adds the safe contract. Small transport effort, medium/high contract effort. |
| B. Narrow authenticated Prox adapter over CPA | One stable, redacted capability contract for Prox; central authorization and controlled routing; avoids exposing CPA internals in browser components. | Requires an available adapter service and a maintained CPA authentication mechanism. An adapter that calculates costs, opens CPA SQLite, or fetches arbitrary user-supplied origins would violate the design. | **Recommended.** Medium transport effort, medium/high owner-contract effort. Best fit for integrated Prox deployments already using a server companion. |
| C. Dedicated analytics service fed by CPA's existing collector | Independent query scaling and retention; can isolate expensive analytical workloads. | Adds a second store, migration/retention policy, delivery guarantees and reconciliation. Without a durable post-persistence feed, loss between collection and export is hidden. Reimplementing normalization/pricing creates two owners. | Defer until measured CPA query or retention limits justify it. High effort. Must be a CPA-maintained projection, never a competing queue consumer. |
| D. External observability platform | Strong operational charts, alerting, trace navigation and potentially long retention. | Provider-specific token accounting, equivalent cost and registered unused models still require CPA contracts. Sampling/cardinality limits, data export, redaction and ongoing platform cost need decisions. Vendor dashboards do not solve missing original data. | Optional operational supplement. Medium integration plus shared contract work; high effort if forced to replace the full requested product. |

Useful hybrids:

- **B plus CPA materialized queries:** start with existing CPA query/rollup owners; add indices or projections there only when representative workload measurements justify them. No new ledger or message bus is required for the first release.
- **B plus A as a deployment mode:** expose one CPA-owned analytical DTO and permit either an adapter or an explicit direct CPA connection. Keep transport selection behind one client contract. Do not implement two accounting paths or an automatic legacy fallback.
- **B plus D for operations:** export redacted, low-cardinality metrics from CPA for alerting while Prox remains the request/cost/model-rate UI. The external platform is not the billing authority.
- **B evolving to C:** later move CPA's query projection behind a service boundary using a durable outbox written with the original event transaction. CPA still owns event normalization and pricing. Export retries must not block the sole collector from keeping up with the short core retention window.
- **Link to CPA as an interim:** a deliberately labeled link to CPA's existing analytics can deliver immediate access after separate authentication. It is a limited interim release, not completion of the requested Prox tab.

Do not federate several CPAs by summing browser responses. Overlapping collection, incompatible rate revisions and nonmergeable percentiles make that unsafe. Prefer one CPA query authority over the configured instance set. If separate CPA stores are mandatory, extend the CPA query owner with explicit dataset identity, disjointness/deduplication rules and mergeable statistics; Prox should transport that result.

## 3. Maintained ownership and boundaries

| Concern | Owner and required public contract |
|---|---|
| Measurement | Core emits observed usage and timing, execution ID and request ID. Future timing-kind/origin fields originate here; CPA must not guess them from provider name alone. |
| Collection | CPA collector owns one active consumption path per logical core queue. Attach the configured stable instance ID before normalization/persistence. Configuration aliases must resolve to one instance. No Prox usage polling or subscription. |
| Event normalization and identity | CPA usage domain owns provider/executor semantics, field availability, event schema revision and attempt deduplication. Add source identity via an explicit mapping to existing Prox/deployment instance IDs, not by copying or inventing a competing registry. |
| Pricing | CPA pricing/model-price services own rate selection, provider/model mapping, revision policy, rounding and coverage. All CPA and Prox views call those results. A model namespace/provider extension belongs here. |
| Persistence and retention | CPA repositories own raw events, projections, migrations, archival and retention coverage. Preserve older data and existing hashes/keys during additive migration; mark unresolvable identity rather than rewriting it heuristically. |
| Queries | CPA monitoring/usage services own filtering, aggregation, percentiles, cost breakdowns, joined model/rate inventory and redacted DTOs. Add a rules document at the owning package and tests at these boundaries. |
| Authentication and transport | Prox adapter validates session authorization for every requested instance; maps only configured CPA destinations; validates query limits; forwards allowlisted calls. It must use supported CPA panel/service authentication, not fabricate equivalence to v8 credentials. No arbitrary proxy, raw SQL, pricing math, or persisted analytical copy. |
| Frontend | Prox analytics feature owns view state, URL filters, chart geometry, formatting, accessible tables, drilldown and cancellation. Existing source registry/session lifetimes fence stale results. A new CPA transport must preserve those owner-generation guards without changing the v8 core client into a v0 client. |

An adapter is a proposed boundary, not an existing credential-delegation feature. Implementation starts by specifying the supported CPA read authorization mechanism. Until then show “Analytics connection required/unavailable”; never fall back to core usage consumption. Portable deployments without the adapter can use an explicit direct CPA capability later or remain unsupported with a clear state.

For several instances collected into one CPA, query once using authorized instance IDs. Do not query the same shared dataset once per selected instance and add the results. One failing source leaves the others visible but the combined result partial. Instance ID, credential source, execution provider and model publisher remain separate dimensions.

## 4. Query and measurement contract

Every response should carry the query scope and bounds, dataset identity, source configuration revision, generated-at time, collection watermarks, rate/normalization revision, per-instance availability and per-metric coverage. Every metric needs a value or null, eligible sample count, applicable population count, unit, measurement definition and omission reasons. Proposed states: known, partial, unknown, unsupported, stale, aggregate-only. These fields extend current CPA coverage; their implementation is not established by this report.

Use UTC instants with half-open bounds `[from, to)` throughout the proposed contract. Display an explicit timezone and have CPA apply calendar buckets consistently, including DST. Confirm current boundary behavior in implementation tests before adapting it. Request only visible panels through CPA's existing selective query pattern. Cursor pagination uses a stable timestamp plus tie-break identity and a query watermark; changing filters invalidates the cursor. Do not load the entire ledger into the browser.

### Counts and denominators

Let **E** be deduplicated retained execution events in the authorized instance set and selected time/filter scope. Until execution identity is available, call these **retained events**, not verified attempts. Let **U** be rows whose identity or instance attribution remains unresolved. Keep U explicit; do not silently assign it to the active instance.

| Metric | Exact proposed definition | Partial/unknown behavior |
|---|---|---|
| Retained events / attempts | `count(E)`; “attempts” only for events with the validated attempt contract. | Separate count of unresolved legacy rows; not an estimate of all client traffic. Do not add raw event counts to overlapping rollup counts. |
| Client requests | Distinct `(instance ID, parent request ID)` among E with verified parent semantics; count by the matching-attempt cohort. | Show linked-attempt coverage `linked attempts / E`. Parents can span the time boundary or several model filters. Count unique parents within each view; per-model parent counts are not additive. |
| Attempt failure rate | Failed attempts divided by attempts with known terminal status; success is the corresponding complement only within that set. | Also show status-known count / E. Retried failed attempts remain failures even if a later attempt succeeds. |
| Client success / retry rate | Only for complete parent groups with an authoritative terminal client outcome: successes / terminal-known groups; groups with more than one execution / complete groups. | Attempt outcomes alone cannot establish client outcome. Omit client success if no terminal evidence. Retain partial groups rather than inventing their final state. |
| Input/output totals | Sum each disjoint normalized token bucket over events eligible for that bucket. | Report eligible event count / E for each bucket. A legacy numeric zero without presence evidence is “reported zero; presence unknown,” not proof of zero consumption. |
| Cache read share | `sum(cache-read input) / sum(total normalized input)` on the same events with known cache semantics and positive denominator. | Coverage is cache-semantic-eligible / E. This is a token share, not a request hit rate. Zero denominator gives N/A. |
| Requests with cache reads | Events with cache read > 0 divided by events with known cache-read observation. | Label “attempts/events with cache reads”; no eligibility guess from unsupported providers. |
| Equivalent API cost | Sum fully priced event costs under one named valuation basis; optionally show a separately labeled known-component subtotal for partially priced events. | Fully priced events / E and unpriced counts by reason are mandatory. Do not claim a total when components are unknown. Include billable usage on failures and retries. |
| Average cost | Fully priced cost subtotal / fully priced events. | Label “per priced attempt/event.” Cost per client request requires complete parent groups with all attempt costs known; use only those groups in both numerator and denominator. |
| Response duration | Median/p95 over events with a valid nonnegative duration of the same measurement kind/origin. | Display measured sample count / applicable E; default success-only performance cohort, with failures separately selectable. Do not claim browser-observed end-to-end duration from an upstream measurement. |
| TTFT / first byte | Median/p95 in separate timing-kind cohorts. True TTFT requires evidence of first substantive token and a stated start boundary. | Legacy unlabeled TTFT is “reported first-response delay; kind unknown.” No pooled cross-kind percentile labeled TTFT. |
| Output over response duration | Per-event `reported output tokens / (latency_ms / 1000)` for known output > 0 and latency > 0; display median/p95 of those event rates. | This matches the inspected CPA speed formula. Coverage denominator is successful output-bearing events in scope. It includes startup delay and is not pure generation speed. |
| Post-first-token output rate | Optional estimate `normalized output tokens / ((completion-start − first-token-start)/1000)` only for comparable clocks, substantive-token provenance, known output and positive interval. | Label “estimated output after first token,” with exact formula. First-token chunk size is unknown, so this is not exact token cadence. Omit for legacy/fallback measurements or incomparable timing origins. |
| Traffic rate | Retained events per explicit bucket duration in seconds; token throughput is reported eligible tokens per bucket duration. | Gaps remain unknown. Do not divide by the sum of request latencies and call it wall-clock throughput. |

Percentiles must come from raw eligible measurements or a declared mergeable histogram/sketch with its error bound. Never average p95s across instances or buckets. For a weighted throughput measure use `sum(output)/sum(duration)` with a distinct label; do not silently substitute it for the median event rate. Historical rollups containing only sums/counts cannot reconstruct p95 or individual requests.

Coverage has four independent axes: collection continuity, raw retention, field measurement, and pricing completeness. “No known raw deletion” is not “100% of traffic collected.” Without an independent emitted-event counter, the fraction of all traffic captured is unknown. Show known gaps, collection start/watermark and unknown continuity rather than manufacturing a capture percentage.

## 5. Analytics information architecture

One top-level **Analytics** entry with six secondary views keeps the requested scope discoverable without six new primary navigation items. Preserve source selection and date filters across views. Initial view is Overview. Use shared metric and breakdown components; no independent formulas per chart.

Global controls: date range/timezone, configured instance(s), execution provider, requested/resolved model selector with explicit mode, outcome, streaming mode and valuation basis. Advanced filters: service tier, endpoint class, opaque credential alias, cache observation state and measurement quality. Only enable server-supported filters; never display a selected instance filter over an unscoped CPA response. Include “Unknown” categories. Model Rates has its own current-registration scope, clearly separate from the historical date range.

Dashboards may show verified zero only for a known observation; use gaps or null with a reason for unknown data. Period comparisons need equivalent filters and comparable coverage; omit percentage change when the baseline is zero and show the absolute change instead.

## 6. Token semantics and price policy

**Normalize once in CPA, then price there.** Preserve reported fields alongside normalized disjoint buckets and a normalization revision. The existing three cache modes are a strong foundation. Cache read and creation mirrors/legacy fields must not be added twice. Determine reasoning inclusion from the protocol/model accounting contract; never universally compute output + reasoning. Keep unknown output semantics explicit. The existing fallback total arithmetic is not sufficient proof that every protocol reports disjoint reasoning.

The general fully known token cost is `(uncached input × input rate + cache read × read rate + cache write × write rate + billable output × output rate) / 1,000,000`, after owner-selected context/tier rules. This equation describes the contract, not permission to duplicate existing calculations. Non-token fees, image/audio units, search/tool charges and cache-storage durations require explicit billing units and measurements; if absent, label the estimate “token cost only” and list omitted components. Do not imply an invoice-equivalent total.

Rate selection should carry explicit provider namespace, canonical billing model, requested/resolved/response-model evidence, service tier, context band, currency, unit and provenance. Existing resolved-first candidate and tier logic remains authoritative until an independently verified rule change. Expose explicit configured zero prices separately from missing prices. Built-in or inferred fallback prices must be labeled estimates; a symbol or comment calling a price “official” is not current external verification.

Recommended valuation policy:

1. **Initial release: current configured rates.** Label every historical amount “Equivalent API cost at current configured rates,” return the rate-book revision/as-of time, and explain that edits may change historical estimates. Existing snapshot consistency supports this mode. Where the old API cannot distinguish unknown from zero, extend CPA's result contract before claiming cost coverage.
2. **Immutable revisions in CPA:** persist each rate book revision with provenance, publication/effective time when known, ingestion time and override reason. Version rate selection and token normalization separately. Add dimensions to the existing pricing owner rather than establishing a second provider-price table in Prox.
3. **Optional event-time estimate:** select the version known to apply to the event's time, or freeze the event's selected rate revision going forward. Late published/corrected rates create explicit revisions and labeled restatements. Never overwrite the original reported usage. Old events with no verified applicable rate history remain historical-rate unknown; current rates are available only through the explicitly selected current-rate mode.
4. **Reproducibility:** a cost detail/export includes valuation basis, rate and normalization revisions, billing-model mapping and priced components. Round at the established owner boundary, retain calculation precision and keep currency-separated sums. Preserve existing clamps/rounding in a behavior-preserving refactor before changing policy; compare representative cost outputs before and after.

Do not make historical-rate support a prerequisite for the first honest current-rate dashboard. Do make rate provenance, unpriced coverage and stable revision identification prerequisites for claiming reproducible costs.

## 7. Request metadata and privacy

“Every request metadata” means every retained, authorized field with its availability status; it does not mean arbitrary raw payload disclosure. CPA's internal event and monitoring response already differ: raw failure bodies are internal, while monitoring rows can include IPs, forwarding chains, user agents, account snapshots and token fingerprints. Authentication alone is not an adequate default projection for a dashboard.

The CPA query owner should return an allowlisted summary by default: opaque request/attempt IDs, stable instance ID, provider, model identities, timestamp, method, sanitized endpoint class, streaming flag, reasoning setting, requested/effective tier where available, normalized tokens, measurement kinds, status, bounded sanitized error summary, pricing provenance and completeness. Treat request IDs and errors as untrusted display text. Path query strings and embedded identifiers need removal at the owner boundary.

Default omitted fields: raw JSON; prompts/completions; raw error bodies; authorization/cookies/headers; keys and token fingerprints; credential filenames; account emails and project/account identifiers; client IP/forwarding chains; full user agent; sensitive session/trace identifiers. Use opaque aliases for allowed filters. Separate privileged detail projection can reveal a specifically authorized subset, with equivalent restrictions on export. Never send sensitive fields to the browser merely to hide columns. Reuse and extend CPA's existing sanitization contract; do not invent a second regex scrubber in Prox. Copy/export actions use the same safe DTO and do not bypass the detail policy.

For each drawer field distinguish not reported, not retained, redacted, unsupported and invalid. Legacy integer fields may not distinguish missing from zero; retain that limitation instead of backfilling certainty. Parent/attempt reconstruction is allowed only from validated identifiers or retained payload evidence under the owner contract, not matching timestamps, model names or credential labels.

### Risks that can change the recommendation

- **CPA cannot provide supported read authentication:** direct integration and adapter both need an explicit service contract. Do not borrow credentials across auth scopes. A separate explicit CPA login may be the smaller first release.
- **History lacks instance/execution identity:** all-instance legacy totals can remain available if CPA can safely authorize the whole dataset; per-instance legacy totals and exact retries stay unavailable. Do not “repair” them by assuming credential identity identifies the source.
- **Retention removes detail:** preserved aggregates can support totals but not all filters, percentiles or request drawers. CPA's coverage limitations must survive every adapter transformation. No promise to replay missing history.
- **Price namespace collision or unsupported units:** expose ambiguous/unpriced coverage and repair CPA's model-price ownership. A Prox-local exception table would perpetuate disagreement between products.
- **CPA query load is too high:** measure on synthetic/approved retained datasets later, use bounded queries and existing rollups first, then consider C. This research establishes no production performance claim.
- **Legacy data collapse:** already-normalized missing fields or hash collisions cannot necessarily be recovered. Preserve originals and name uncertainty; do not derive a historical guarantee from a new schema.
