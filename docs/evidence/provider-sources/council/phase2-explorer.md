# Council Phase 2 — internal evidence research

The existing architecture is one mutable management connection plus a quota-history service with two provider-to-port mappings. Extending the switcher would expose one inventory at a time, but would not provide the enumerable, multi-instance ownership contract requested in the brief. The principal blockers are source-local identity, operation ownership, global response effects, and history retirement. Pagination does not explain the missing Claude inventory in the inspected code.

## 1. Shared transport, identity and refresh

**One mutable transport.** `ApiClient` is private to its module; the exported instance is a singleton. `setConfig` advances a revision when base/key changes, and the request interceptor reads the current base/key. `captureConnection()` creates a client pinned to captured values and suppresses response events after a parent revision change, including A→B→A. It is an existing extension seam, not a safe basis for repeatedly swapping the global client to enumerate sources. [src/services/api/client.ts:19](/home/swerve/src/prox/src/services/api/client.ts:19), [src/services/api/client.ts:39](/home/swerve/src/prox/src/services/api/client.ts:39), [src/services/api/client.ts:60](/home/swerve/src/prox/src/services/api/client.ts:60), [src/services/api/client.ts:122](/home/swerve/src/prox/src/services/api/client.ts:122), [src/services/api/client.ts:272](/home/swerve/src/prox/src/services/api/client.ts:272).

**Global side effects.** Version/build and plugin-support events have no instance owner. An unsuppressed 401 dispatches `unauthorized`, whose listener logs out and clears global caches. A secondary source's 401 cannot use this contract unchanged. Capturing a connection suppresses stale effects after a revision change; it does not establish independent authentication state for concurrently active sources. [src/services/api/client.ts:139](/home/swerve/src/prox/src/services/api/client.ts:139), [src/services/api/client.ts:174](/home/swerve/src/prox/src/services/api/client.ts:174), [src/stores/useAuthStore.ts:243](/home/swerve/src/prox/src/stores/useAuthStore.ts:243).

**Transport and store identity can temporarily disagree.** Login clears config/models/quota and changes the singleton before validating config. Only after success does it publish the new auth-store base/key. Checking store identity alone does not guard this intermediate interval. [src/stores/useAuthStore.ts:94](/home/swerve/src/prox/src/stores/useAuthStore.ts:94).

**Portable connections versus deployed choices.** The connection helper accepts arbitrary backend bases and appends the v8 management prefix. The runtime selector recognizes only same-origin root, `/codex` and `/claude`; provider and instance are conflated. `ManagementRuntime` calls global login using the current management key. Layout only renders it for detailed quotas and logs. [src/utils/connection.ts:3](/home/swerve/src/prox/src/utils/connection.ts:3), [src/features/quotaPool/runtimeConnection.ts:5](/home/swerve/src/prox/src/features/quotaPool/runtimeConnection.ts:5), [src/features/quotaPool/ManagementRuntime.tsx:16](/home/swerve/src/prox/src/features/quotaPool/ManagementRuntime.tsx:16), [src/components/layout/MainLayout.tsx:1216](/home/swerve/src/prox/src/components/layout/MainLayout.tsx:1216).

**Caches have different guards.** Config has one full-config TTL cache, in-flight request and token; its guard prevents stale store publication but a stale promise can still return data to a caller. TTL is 30 seconds. Models has one base+client-key cache with a request-token guard. Quotas has provider maps, a global generation and filename invalidation generations. Instance scoping must retain these distinct protections. [src/stores/useConfigStore.ts:27](/home/swerve/src/prox/src/stores/useConfigStore.ts:27), [src/utils/constants.ts:13](/home/swerve/src/prox/src/utils/constants.ts:13), [src/stores/useModelsStore.ts:10](/home/swerve/src/prox/src/stores/useModelsStore.ts:10), [src/stores/useQuotaStore.ts:20](/home/swerve/src/prox/src/stores/useQuotaStore.ts:20), [src/stores/useQuotaStore.ts:116](/home/swerve/src/prox/src/stores/useQuotaStore.ts:116).

**Refresh has consumers outside pages.** Header refresh supports one registered page handler. Layout separately loads credential count and plugin menus; refresh reloads config, menus, count and page data. Credential count has a request guard; menu loading lacks equivalent ownership protection throughout. Auth-file and plugin-resource events carry no source payload, and global plugin support gates routes. A page-only registry misses these consumers. ## 5. Four-option compatibility assessment

### 1. Global switcher everywhere

Reuses login/cache clearing and existing prefixes, and could select the Claude-local list. It still fails simultaneous enumeration/aggregation, cannot represent multiple same-provider or mixed-provider instances through provider-named choices, and leaves stale confirmation/download actions, independent pool history and missing catalog/resource routes unresolved. It is a compatibility baseline, not the complete fix.

### 2. Browser registry and scoped clients

Domain API modules and captured-client precedent provide concrete extension points. A browser-only list, however, is not authoritative for nginx or the collector. It needs independent transport/auth/capability/error state, scoped caches/events/results, and ownership through complete chains: discovery pagination, OAuth and plugin polling included. Repeated `setConfig()` is incompatible with those asynchronous chains.

Checked-in CORS does not establish direct browser network/auth viability; shared management keys are unverified. Naming sources cannot repair missing deployed catalog/resource routes. Pool retirement, identity and migration remain separate necessary work.

### 3. Server registry and relay

The existing Bun service is quota-only. A management relay is a new transport responsibility, and nginx currently bypasses it for ordinary management. A JSON-only GET/POST wrapper is incompatible with PATCH/PUT/DELETE bodies, multipart uploads, blobs/log downloads, YAML/scalar config, response statuses/errors/headers, long refreshes, OAuth callback exceptions and backend-declared plugin paths. Client-key catalogs need distinct authentication semantics.

The server currently has one file-backed key, no source registry and no per-source auth configuration. Relay discovery/auth/aggregate partial-result contracts are not already implemented. This option still needs source-bearing browser identities/drafts, history migration, LAN routing and portable single-backend compatibility. An unavailable mutation owner must not trigger fallback to another instance.

### 4. Manifest, generated routes and scoped clients

Compatible with retaining nginx transport and existing quota-domain aggregation if the manifest truly drives browser enumeration, routing and collector origins. No shared authority exists in the inspected files: nginx, runtime selector and collector encode their own mappings. A new browser array alone would leave duplicate authorities.

It inherits option 2's identity/cache/event/operation requirements, plus route generation/validation for management, client catalogs and declared plugin paths. It must preserve standalone external connections and distinguish missing/failed discovery from valid empty inventory. Manifest data must not replace provider descriptors or quota rules. History migration and repeated-allowance treatment remain unresolved by routing generation.

The smallest coherent boundary supported by the evidence is one instance inventory consumed by routing/browser/collector, scoped domain APIs, and aggregation retained in its existing quota owner. Relay versus deployment generation remains the council's architecture choice; neither complete multi-source mechanism is shipped here.

## 6. Contracts to extend once; scope decisions the implementation must make

- Instance identity is independent of provider kind and of existing credential/provider/plugin “source” fields.
- Scope transport revisions and auth/capability/error events at the API boundary, then carry ownership through domain APIs. Page-only changes miss layout, stores and background operations.
- Normalize each source's inventory before combining it. Preserve physical-file and auth-index semantics. Scope selections, request signatures, queues, cache entries and invalidation.
- Inventory/count/activity aggregation requires source completeness/error results. Existing recent-usage failure-as-cache is insufficient proof of a complete aggregate.
- Config drafts, group writes, log cursors/clear, plugin operations, OAuth, uploads and credential mutations require an explicit owner. “All” must resolve to concrete owned targets before execution and preserve partial/unknown outcomes, especially after timeout. Backend `all=true` is source-local.
- History needs source-local retirement and deliberate legacy-ID migration. Independent allowance identity is a separate quota-domain question; neither namespacing nor email deduplication proves capacity.
- Deployment inventory owns origins/routing, while existing provider descriptors and quota rules retain their domain responsibilities.

These are constraints from existing call graphs and the brief, not proposed UI layouts.
